# iwo Calendar Bridge — план (v5)

Односторонний перенос событий календаря из домена 1 (только чтение, через Outlook) в основной календарь
выбранного ящика домена 2 (через EWS). Десктопное приложение на C# с GUI и менеджером заданий.
Первый выпуск — очистка основного календаря от событий, оставленных прежним приложением.

Статус: выпуск R1 в работе — ядро, сценарий очистки и адаптер EWS реализованы и покрыты тестами;
интеграционная проверка на сервере и GUI впереди.

История ревизий:
- v1 — архитектура и правила переноса.
- v2 — надёжность: окно и удаление, ключ исключений, идемпотентность вложений, COM, параллелизм.
- v3 — реестр ловушек T1–T25.
- v4 — сокращение объёма по DRY/KISS/SOLID/YAGNI/SoC; `LastModificationTime`; дефолт очистки; T26–T29.
- v5 — **очистка первым выпуском; приёмник — основной календарь выбранного ящика.** Исправлено: время
  (фиксированное смещение пояса из профиля вместо «чистого UTC», T31); семантика очистки по периоду (§8); перечисление
  при огромном объёме и удаление без пропусков (T30, T32); адрес в подтверждении стал реальной целью
  запросов (T33); описание риска квоты (T4); рекомендация рантайма (§11). Добавлены T34, T35.

## 0. Принципы и что из плана вырезано

Принципы применяются к объёму работ, а не только к коду.

**Мультиарендность — никаких данных организации в продукте (T36).** Адрес сервера, SMTP-адрес ящика,
смещение пояса, отпечаток сертификата и учётные данные — только пользовательская конфигурация (профиль
подключения `config/connection.json` + диспетчер учётных данных Windows). В исходниках, документах,
тестовых данных и логах нет названий организаций, адресов, имён серверов и отпечатков. Любая организация
подставляет свои данные, ничего не меняя в коде. Тесты используют синтетические данные.

**Вырезано (YAGNI):**
- *Несколько заданий и пар календарей.* Нужна одна пара: общий календарь домена 1 → основной календарь
  выбранного ящика домена 2.
- *Выбор папки-приёмника (v5).* Пишем в основной календарь: Android-клиент читает только его (T35).
  Выбор ящика (учётки) остаётся.
- *Второй движок переноса серий отдельными событиями.* Расхождение сверки серии — предупреждение в журнале.
- *Отдельный режим восстановления карты.* Это тот же поиск по метке, что в обычном пути: кэш → промах →
  сервер.
- *Фильтры, отчёты, inline-HTML, UI-автотесты, мутационное тестирование* — вне MVP.
- *Конвертация RTF→HTML* — вне MVP, описание переносится текстом.
- *Режим очистки «только копии моста» в R1 (v5).* До появления моста копий нет. Режим добавляется в R2 и
  становится режимом по умолчанию.

**DRY — одна реализация на каждое правило:** `TimeMapper` (нормализация к UTC), `TargetTimeZone` (пояс из
конфигурации, «весь день», границы периода), `ContentHasher`, `ErrorClassifier`, `CompletenessGuard`,
`CalendarSnapshotReader` (единственный постраничный
обход календаря приёмника — и для очистки, и для снимка приёмника в мосте), `AttachmentReconciler`,
`SeriesWriter`, `Executor.Upsert`.

**SOLID:** SRP — `Planner` и `CleanupPlanner` чистые функции (снимки → план), `Executor` и `CleanupRunner`
применяют план, `RunGuards` — лимиты и авторитетность, `Scheduler` — время. ISP — порты `ISourceReader`
(только чтение), `ITargetReader`, `ITargetWriter`. DIP — ядро зависит только от портов. OCP — новое поле
события добавляется в модель и два маппера, без правки ядра.

**SoC:** `IwoBridge.Core` не ссылается ни на Outlook Interop, ни на EWS — проверяется архитектурным тестом.
Время преобразуется только в `TimeMapper`.

**KISS:** одна пара календарей, одна дорога записи, кэш вместо второго источника правды, текст вместо
конвертеров, журнал и манифест как носители прогресса.

## 1. Цель и границы

**Цель.** Сначала очистить основной календарь ящика домена 2 от событий прежнего приложения. Затем
периодически и по кнопке держать этот календарь зеркалом общего календаря домена 1: создано — создаётся,
изменено — обновляется, удалено — удаляется. Переносятся вложения, серии переносятся сериями, дублей нет.

**Выпуски** (подробно — `WORKPLAN.md`): R1 — очистка; R2 — синхронизация; R3 — стабилизация и приёмка.

**В границах:** источник — общий ящик в Outlook 2013 (только чтение); приёмник — **основной календарь**
выбранного ящика домена 2, вход под доменной учёткой этого ящика; односторонняя синхронизация 1 → 2 с
настраиваемым интервалом и ручным запуском; поля — тема, время, место, описание (текст), напоминание,
статус занятости, приватность, вложения-файлы, повторения с исключениями; очистка приёмника.

**Вне границ:** запись в домен 1; обратная синхронизация; рассылка приглашений; перенос встреч встречами
(§6.2); несколько заданий; выбор папки-приёмника; запись в чужой ящик (Impersonation/делегат); календари
общих папок; конвертация RTF→HTML.

**Нефункциональные требования:** без багов, крашей, зависаний, утечек памяти, деградации и логических
ошибок; DRY, KISS, SOLID, YAGNI, SoC; выверенный UI/UX; реальные тесты; сверка с внешними источниками;
совместимость вплоть до Exchange 2013 с последним пакетом обновления.

| Параметр | Значение |
|---|---|
| ОС | Windows 10 Pro 22H2 (10.0.19045), x64 |
| Outlook | Outlook 2013 (15.0), x64 — профиль домена 1, общий календарь read-only |

| .NET SDK | 8.0.x |
| Часовой пояс приёмника | Настраивается: фиксированное смещение UTC, без перехода на летнее время |
| Антивирус | Kaspersky Endpoint Security 12.12 + Windows Defender |

**Приёмник (домен 2):** Exchange 2007 SP2 на Windows Server 2003 R2 — целевой класс сервера.
Адрес EWS, SMTP-адрес ящика и смещение пояса задаются в профиле подключения (§11, T36); конкретных
значений в документах нет. Папка — основной календарь ящика.

**Канал:** при проверке наблюдались TLS 1.0, 3DES-168, RSA, SHA1; EWS отвечает `401 Negotiate/NTLM`.
Сертификат выписан на имя сервера, а не на адрес подключения → закрепление по отпечатку (§9).

**Блокер (среда разработки):** Kaspersky перехватывает HTTPS и подменяет сертификат, из-за чего
соединение к серверу зависает. На время работ антивирус отключён; для постоянной работы адрес EWS
вносится в исключения проверки защищённых соединений. Приложение детектирует подменённый CA (T21) и
даёт понятную ошибку.

## 3. Опора на существующий код (домен 2, EWS)

Референсный EAS/EWS-клиент (отдельный проект) уже работает с Exchange 2007 по EWS/NTLM. Его решения —
проверенные против реального сервера факты (имена модулей ниже — технические, без данных организации):

- **Читает только основной календарь:** в EAS — папку типа 8 (основной календарь; пользовательские
  календари имеют тип 13) в `eas/EasCalendarSyncService.kt`, в EWS — `DistinguishedFolderId Id="calendar"`.
  Подпапку телефон не увидит, поэтому приёмник — основной календарь (T35).
- **Цикл EAS-синхронизации ограничен:** до 100 итераций по 100 изменений и до 5 минут, иначе снимок
  помечается неавторитетным (`eas/EasCalendarSyncService.kt`). После удаления больше 10 000 событий
  телефон догонит изменения за несколько циклов.
- **NTLM** аутентифицирует TCP-соединение: Type1/Type3 по одному соединению, тело 401 дочитывается
  полностью (`eas/EwsClient.kt`). В C# — `HttpWebRequest` + `CredentialCache("NTLM")`.
- **Схема** — `Exchange2007_SP1` (база для 2007 SP2 → 2013).
- **Правила повтора** (`eas/CalendarRecurrenceBuilder.kt`); в клиенте захардкожены `Interval=1` и
  `NoEndRecurrence` — мосту мало (§6.4).
- **Исключения серий**: «мастер + изменённые/удалённые повторения», раскрытие через `CalendarView`,
  у изменённого `CalendarItemType = Exception` (`eas/CalendarExceptionService.kt`).
- **Удаление отдельного повторения** — `CalendarView` + `DeleteItem` по id повторения
  (`deleteSingleOccurrenceEws` в `eas/EasCalendarCrudService.kt`). Используем в очистке для серий на
  границе периода (§8).
- **Вложения** только через EWS; `CalendarView` отдаёт лишь `HasAttachments`, детали — `GetItem`;
  `CalendarView` и `Restriction` несовместимы в одном `FindItem`; вложения серии на мастере; цепочка
  загрузок обновляет `RootItemChangeKey` (`eas/CalendarAttachmentService.kt`).
- **«Весь день» = полночь UTC** — так клиент создаёт события в своём EAS-пути с поясом UTC
  (`eas/EasCalendarCrudService.kt`). Мосту это правило **не подходит**: копии создаются в поясе приёмника из профиля
  (§6.4, T31).
- **Пакетное удаление** строго: успех только если учтены все id; частичный результат — ошибка;
  `ErrorItemNotFound` — идемпотентный успех (`evaluateBatchDeleteResponse` + тест).
- **`isAuthoritativeSnapshot`** — снимок с обрывами не используется для разрушительных решений.
  Переносим на источник (T2).
- Матч по **subject+time** в клиенте для моста не годится: копии опознаём только по метке (§5).

## 4. Архитектура

```
GUI (WPF, MVVM): подключение • очистка (R1) • прогон • план • журнал • настройки (R2)
        │
Application: CleanupRunner (R1) • SyncRunner • Scheduler (R2)
   ├── Core: CleanupPlanner • Planner • Executor • RunGuards • TimeMapper • ContentHasher
   │         ErrorClassifier • CompletenessGuard • AttachmentReconciler • SeriesWriter
   ├── ITargetPageReader/ITargetDeleter/… → EWS-адаптер (страницы, данные серий, окно, удаление)
   │                                 → HTTPS/NTLM/TLS1.0 → Exchange 2007 (домен 2)
   ├── ISourceReader  → Outlook-адаптер (COM, STA, IMessageFilter) → Exchange 2007 (домен 1)  [R2]
   ├── IStateStore      → SQLite (кэш карты, ватермарка, журнал)  [R2]
   └── ICredentialStore → Windows Credential Manager (DPAPI)
```

**Модель события:** `CalendarEvent` { sourceId, subject, start(UTC), end(UTC), isAllDay, location,
bodyText, sensitivity, busyStatus, reminderMinutes, organizer, attendees[], recurrence?, exceptions[],
attachments[](name, size, kind), lastModified, contentHash }.

**Элемент приёмника:** `TargetItemInfo` { itemId, itemClass, kind (Single/RecurringMaster), start, end,
uid, firstOccurrence?, lastOccurrence?, bridgeMarker? } — вход `CleanupPlanner` и `Planner`.

**Снимок источника:** `SourceSnapshot` { events[], window, **isAuthoritative**, warnings[] }.
Разрушительные решения — только по авторитетному снимку (T2).

## 5. Идемпотентность, окно, удаление (мост, R2)

**Метка на копии** (расширенные свойства EWS, именованные, собственный GUID-набор; проверено — создаются
`SetExtendedProperty`, ищутся `FindItems` с фильтром на Exchange 2007 SP1):
- `IwoBridgeSourceId` — `GlobalAppointmentID` / `PidLidGlobalObjectId` (hex); для серии — на мастер;
- `IwoBridgeContentHash` — хэш нормализованного содержимого;
- `IwoBridgeSourceFolder` — id исходной папки (T26).

**Поиск перед записью:** локальный кэш → промах → `FindItems` по `IwoBridgeSourceId` **в основном
календаре** (не по ящику, T23). Одна дорога. Несколько совпадений (метку наследуют исключения)
разрешаются детерминированно, предпочтение `RecurringMaster` (T13).

**Ключ исключения серии:** `seriesSourceId + OriginalDate` (UTC). Вырожденный или дублирующийся id —
составной ключ (sourceId + start) и пометка (T24).

**Diff-прогон (`Core.Sync.SyncPlanner`, чистая функция, сделан и покрыт тестами):** `source\target` →
создать; изменилось → обновить; `target\source` среди наших → удалить; иначе пропустить. События без метки
(в том числе твои личные в основном календаре) не трогаются никогда.

**Перезапись периода — точечная, не полная.** Пользователь выбирает период; копии периода не стираются и
не заливаются заново, а сравниваются с источником по метке и отпечатку:

| Источник | Копия моста | Действие |
|---|---|---|
| есть, в периоде | нет | создать |
| есть | есть, отпечаток тот же | не трогать |
| есть | есть, отпечаток другой или его нет | перезаписать (`UpdateItem`, содержимое и отпечаток разом) |
| есть, вид сменился (одиночное ↔ серия) | есть | пересоздать |
| нет (удалено) | есть, в периоде | удалить (`SendToNone`) |
| — | несколько копий одного события | лишние удалить, одну оставить |
| перенесено за период | есть, в периоде | перезаписать — копия переезжает, а не удаляется |

- Отпечаток (`SyncContent.Hash`, «v1:» + SHA-256) — от темы, места, описания, начала и конца в UTC, «весь
  день», занятости, конфиденциальности, правила повтора, исключений и вложений (имя, размер, SHA-256).
  Напоминаний в нём нет: на копиях они выключены (§6.1). Не зависит от порядка
  вложений и исключений, вида переводов строк и пробелов в концах строк.
- Контракт снимка источника: события, пересекающие период, плюс ещё существующие события, на которые
  ссылаются копии периода (иначе перенос за пределы периода выглядел бы удалением).
- Копии вне периода без события в снимке не трогаются: этот снимок о них ничего не знает.
- Неполный снимок источника → ни одного удаления «удалено в источнике»; создания и перезаписи — да.
- Защита от массового удаления — ниже, «Лимит удаления».
- Серия — единица: сравнивается и переписывается целиком.
- Правка копии в приёмнике руками не обнаруживается: отпечаток на копии — отпечаток источника. Копия
  перезапишется при следующем изменении события в источнике (односторонняя синхронизация).
- Порядок применения: удаление лишнего → пересоздание → перезапись → создание.

**Окно и удаление:** чтение, сверка и удаление — в одном скользящем окне (§6.5). Копия с началом вне
прочитанного окна не удаляется. Ватермарка двигается только при полном успехе прогона.

**Предохранители:**
- *Пробный прогон* — при первом запуске и после любого изменения настроек (T25).
- *Лимит создания* — порог подтверждения, не жёсткий стоп: первичную заливку подтверждаешь один раз в
  пробном прогоне; в автоматических прогонах превышение останавливает работу (T28).
- *Лимит удаления* — не больше 20 за прогон и не больше 10 % копий периода (доля проверяется начиная с
  6 удалений); пустой источник при непустых копиях — всегда подозрителен. Иначе план только показывается,
  применение — после явного подтверждения (T1; `SyncOptions`).
- *Фаза удаления пропускается*, если снимок источника неавторитетный (T2).
- *Прогресс по каждому элементу* пишется сразу, сбой первичной заливки не начинает её заново.
- *Атомарность:* содержимое и новый `IwoBridgeContentHash` — одним `UpdateItem` (T29).

## 6. Правила переноса (R2)

### 6.1. Поля
Тема, время, место, статус занятости — напрямую. **Напоминания** на копиях по умолчанию выключены.
**Описание** — простой текст (`Body`): у `AppointmentItem` нет `HTMLBody`, объектная модель отдаёт только
`Body` и `RTFBody` (T7). В основном календаре статус занятости копий виден коллегам домена 2 при
планировании встреч с тобой (§14).

### 6.2. Встречи → простые события
Копия — простым событием, организатор и участники текстом в начало описания. Атрибуты не путать (T6):
`CreateItem` → `SendMeetingInvitations="SendToNone"` (обязателен для элементов календаря), `UpdateItem` →
`SendMeetingInvitationsOrCancellations="SendToNone"`, `DeleteItem` → `SendMeetingCancellations="SendToNone"`
(обязателен при удалении элементов календаря).

### 6.3. Приватные (Private)
По умолчанию «Занято», без темы, описания и вложений; настраивается. Private-тела и вложения не попадают в
staging и в логи. Невидимость приватных не трактуется как удаление (T18).

### 6.4. Серии — настоящей серией

| Outlook | EWS |
|---|---|
| `olRecursDaily`, `Interval` | `DailyRecurrence` + `Interval` |
| `olRecursWeekly`, `DayOfWeekMask`, `Interval` | `WeeklyRecurrence` + `DaysOfWeek` + `Interval` |
| `olRecursMonthly`, `DayOfMonth`, `Interval` | `AbsoluteMonthlyRecurrence` |
| `olRecursMonthNth`, `Instance`, `DayOfWeekMask` | `RelativeMonthlyRecurrence` + `DayOfWeekIndex` |
| `olRecursYearly`, `DayOfMonth`, `MonthOfYear` | `AbsoluteYearlyRecurrence` |
| `olRecursYearNth`, `Instance`, `MonthOfYear` | `RelativeYearlyRecurrence` |

**Окончание:** признак бессрочности — `NoEndDate`. `NoEndDate = true` → `NoEndRecurrence`, иначе
`EndDateRecurrence` с `PatternEndDate` (T8).

**Исключения** из `RecurrencePattern.Exceptions`: удалённые (по `OriginalDate`) и изменённые. В домене 2
находим повторение на `OriginalDate` и удаляем или меняем — Exchange делает его исключением. Один код на
создание и обновление (`SeriesWriter`).

**Смена узора (T12):** серия пересоздаётся: удалить → создать → применить исключения → загрузить вложения
мастера → атомарно обновить карту.

**Чтение:** `Items.IncludeRecurrences = False` — перечисляем мастера и берём `GetRecurrencePattern`;
раскрытие для сверки делаем сами (`Restrict`/`Find` на повторяющихся ненадёжны).

**Сверка:** раскрытые повторения сравниваем в окне отрезками с делением при усечении (T15). Расхождение —
предупреждение в журнале.

**Время и пояс (исправлено в v5, T31).** Моменты начала и конца копируем точно: `StartUTC`/`EndUTC` из
Outlook. Пояс копии задаём явно — `MeetingTimeZone` с фиксированным смещением из профиля, без перехода на
летнее время, собственным определением, а не именем из реестра сервера.

Почему не «чистый UTC», как было в v3–v4:
- Exchange выравнивает событие «на весь день» по полуночи в поясе запроса или события. В клиенте с другим
  поясом оно показывается с лишними днями или перестаёт быть событием на весь день (документация MS
  «Create all-day events by using EWS»). С Exchange 2007 SP1 это известный случай: событие на весь день
  занимает два дня.
- Правило повтора вычисляется в поясе события. В UTC события с 00:00 до 04:00 местного времени, включая
  все повторяющиеся события на весь день (они начинаются в 20:00 UTC предыдущего дня), попали бы не на
  тот день недели или число.

Собственное определение пояса не зависит от таблиц поясов Server 2003 R2, где нет российских правил
после 2014/2016 (KB2998527, KB3148851) — ради этого и вводился UTC. Все преобразования — только в
`TimeMapper`.

Проверка на прототипе (W5.4): событие на весь день; ежегодное на весь день; еженедельное в 01:00 по
понедельникам; ежемесячное 1-го числа в 00:30; летние и зимние даты. Смотрим в Outlook домена 2, OWA и
Android-клиенте.

### 6.5. Окно
Скользящее, по умолчанию −30…+180 дней, настраивается; задаёт границы чтения, сверки и удаления. Границы —
с допуском на расхождение часов клиента и сервера (T20).

### 6.6. Определение изменений
Первичный признак — `LastModificationTime` события в Outlook (соответствует `PR_LAST_MODIFICATION_TIME`).
Не изменился → пропуск без чтения тела и вложений. Изменился → собираем модель, считаем `contentHash`,
сравниваем с меткой на копии; совпал → обновление не нужно.

`contentHash` — по нормализованной модели: тема, старт и конец в UTC, isAllDay, место, тело, busyStatus,
sensitivity, reminder, правило повтора, все исключения, отпечаток вложений (имя, размер, тип).

*К проверке (W5.2):* обновляется ли `LastModificationTime` мастера при правке одного повторения. Если нет —
для серий дополнительно сверяем список исключений.

## 7. Вложения (R2)

## 8. Очистка основного календаря (выпуск R1)

Назначение: убрать из основного календаря события прежнего приложения до того, как мост начнёт писать.

**Режимы.**
- *Все события* (R1). События прежнего приложения не несут метки моста, их убирает только этот режим.
  Он удаляет всё в выбранном объёме, включая настоящие события и встречи. Уведомления не рассылаются
  (`SendMeetingCancellations="SendToNone"`).
- *Только копии моста* (R2) — тот же конвейер с фильтром по метке; станет режимом по умолчанию (T27).

**Объём:** весь календарь или период «с…по…». Даты местные, конец включительно; границы — местная полночь
по поясу из профиля, переводятся в UTC в `TargetTimeZone`.

**Принадлежность периоду — одно правило `TimeWindow.Overlaps`.** Окно — полуинтервал [начало, конец):
событие с длительностью попадает, если строго пересекает окно; событие нулевой длительности — по началу.
EWS `CalendarView` возвращает надмножество (по документации исключаются только элементы, закончившиеся
*раньше* начала окна, поэтому событие, закончившееся ровно в момент начала, в ответ попадает), и ответ всегда
дофильтровывается этим правилом.

**Семантика периода** (`CleanupPlanner`, чистая функция):
- одиночное событие, пересекающее период, удаляется;
- серия удаляется целиком (мастером), только если в периоде лежат все её экземпляры: повторения по правилу
  (`FirstOccurrence`…`LastOccurrence`) и каждое изменённое повторение (`ModifiedOccurrences`). Исключение,
  перенесённое за пределы периода, запрещает удаление целиком — серия обрезается, перенесённое остаётся;
- серия пропускается, если в периоде нет её экземпляров ни по правилу, ни по факту (раскрытое окно и
  изменённые повторения): исключение, перенесённое *в* период, делает серию граничной;
- остальные серии обрезаются: удаляются только их экземпляры, пересекающие период;
- экземпляры сопоставляются с серией по UID и **только среди повторений и исключений** — одиночное событие
  с тем же UID не удаляется никогда. Серия без UID (`SeriesUidUnavailable`) или с UID, совпадающим с UID
  сохраняемой серии (`AmbiguousSeriesUid`), не обрезается и показывается в предпросмотре с причиной;
- бессрочная серия определяется по `Recurrence.HasEnd`, а не по вычисленному сервером последнему повторению;
- в режиме «весь календарь» удаляются все мастера и одиночные события, раскрытие серий не нужно.

**Перечисление (T30, T32).** Основной объём не раскрываем через `CalendarView`: он режется по числу
элементов, а плотный день с тысячами дублей бесконечно не раздробить.
1. `CalendarSnapshotReader` + `EwsCalendarGateway`: постраничный `FindItem` без раскрытия серий
   (`Traversal="Shallow"`, сортировка по `DateTimeCreated` по возрастанию — новые элементы попадают в конец),
   страница 500 + 1 якорь (не больше 1000 элементов за запрос). Элементы других классов показываются в
   предпросмотре и не удаляются.
2. Полнота — приём «якорного элемента» из документации Microsoft («Perform paged searches by using EWS»):
   следующая страница обязана начинаться с последнего элемента предыдущей. Несовпадение (набор сдвинулся из-за
   удаления или вставки раньше курсора) или расхождение числа уникальных элементов с `TotalItemsInView` в конце
   обхода → обход повторяется с начала (до 3 раз), затем снимок неполный и удаление запрещено.
3. Для мастеров — `GetItem` с `FirstOccurrence`, `LastOccurrence`, `ModifiedOccurrences`, `Recurrence`,
   `UID` (есть в схеме Exchange 2007 SP1). Мастер без первого повторения считается непрочитанным → удаление
   запрещено.
4. `CalendarView` — окно периода, отрезками не длиннее года (защитно); при усечении отрезок делится пополам
   до суток, неустранимое усечение → удаление запрещено.

**Предпросмотр → подтверждение → свежая сверка → удаление (T30).** Сначала все чтения, потом записи.
Пользователь подтверждает предпросмотр; перед удалением строится свежий план, и удаляется только
*пересечение* подтверждённого и свежего: появившееся после предпросмотра не трогается (не было показано),
исчезнувшее или вышедшее из периода — тоже; оба числа видны в отчёте. Затем удаление пакетами по 50 со
строгой оценкой (`ErrorItemNotFound` — успех, частичный результат — ошибка, учтённое до остановки
сообщается). Сначала мастера и одиночные события, затем экземпляры обрезаемых серий. Прерванную очистку можно
запустить снова: уже удалённое даст `ErrorItemNotFound`. Манифест удаляемого (CSV: вид, тема, время, id)
пишется в файл после свежей сверки и до первого удаления — ровно список удаления; не записался — удаления нет.

**Цель — введённый адрес (T33).** Адрес ящика, который вводится для подтверждения, подставляется в запросы
как ящик основного календаря (`DistinguishedFolderId Id="calendar"` + `Mailbox`). Запросы идут ровно в
ящик с введённым адресом: подтверждённое и удаляемое совпадают. Если у учётки нет прав на этот ящик,
сервер откажет и ничего не удалится. В программе папка зафиксирована — основной календарь; в
интеграционных тестах передаётся тестовая подпапка.

**Способ удаления.**
- *В «Удалённые»* (по умолчанию, `MoveToDeletedItems`) — можно вернуть перетаскиванием. Удалённые
  повторения серий так не вернуть — предупреждаем.
- *Окончательно* (`HardDelete` — по документации, удаление из хранилища) — отдельной галочкой с повторным
  подтверждением.

**Квота (T4, исправлено).** Перенос в «Удалённые» не увеличивает ящик. Но мусор продолжает занимать место,
пока лежит там, и первичная заливка поверх может упереться в квоту. После очистки показываем объём в
«Удалённых» и предлагаем очистить их перед заливкой; перед заливкой — проверка квоты (T22).

**Встречи в режиме «все».** На Exchange 2007 нет Calendar Repair Assistant (появился в 2010), удалённые
встречи сами не вернутся. На 2010/2013 CRA может восстановить удалённые встречи, где ящик — участник (T34).

**Предпросмотр:** числа по категориям (одиночные, серии целиком, повторения серий на границе, элементы
других классов) и виртуализированный список, тысячи строк без подвисаний. **Отмена** — после текущего
пакета. **Журнал** — в файл. После очистки — сводка и напоминание про «Удалённые».

## 9. Источник Outlook — надёжность COM (R2)
- **`IMessageFilter`** на STA-потоке: `RPC_E_CALL_REJECTED` / `RPC_E_SERVERCALL_RETRYLATER` → повтор.
- **Один STA-поток** на весь доступ к Outlook, насос сообщений.
- **Дисциплина COM:** `Marshal.ReleaseComObject` в обратном порядке; ссылки на серию и исключения
  переполучаем при каждом доступе; без двухточечных цепочек.
- **Проба прав (T17)** при настройке; **состояние Outlook (T19)** с внятными сообщениями.
- **Кэш общей папки (T2):** снимок неавторитетный при ошибках перечисления, резком падении числа событий,
  признаках недокачанного кэша. Неавторитетный снимок: создание и обновление можно, удаление запрещено.
- **Только чтение:** `ISourceReader` не содержит операций записи; архитектурный тест.
- **Пиннинг сертификата** приёмника по отпечатку; проверку сертификата не отключаем.

## 10. Планировщик, параллелизм, ошибки
- **Неперекрытие (R2):** идёт прогон — следующий тик пропускается; запросы к EWS сериализуются.
- **Один экземпляр (T5):** глобальный мьютекс; в R2 — плюс блокировка в базе.
- **Пропущенные прогоны (R2):** догон от ватермарки при старте и после выхода из сна.
- **Отмена:** оставляет согласованное состояние.
- **`ErrorClassifier` — единственное место классификации:**
  - *временные* (таймаут, 503, сброс, COM-busy, `ErrorServerBusy`) — повтор с нарастающей задержкой и
    джиттером; для 2010/2013 — `BackOffMilliseconds` (T16);
  - *конфликт версии* (устаревший `ChangeKey`) — перечитать и повторить один раз (T14);
  - *постоянные* (`ErrorAccessDenied`, схема, 413, `ErrorQuotaExceeded`, подменённый CA) — без повторов;
  - **аутентификация (T3):** 401 после корректного NTLM-обмена — неверный пароль. Не повторять: доменная
    политика заблокирует учётку. Стоп, учётные данные помечаются недействительными, запрос пароля;
  - частичный успех пакета — стоп.

## 11. Стек

Язык — **C#**. Рантайм — **.NET Framework 4.8** (цель сборки `net48`):
- официальная EWS Managed API 2.2 собрана под .NET Framework;
- 4.8 — последняя версия, доступная на Windows 7 SP1 и 8.1 (4.8.1 для них не выпускается), а программа
  поддерживает Windows 7+; на Windows 10 1903+ и 11 рантайм встроен и обслуживается вместе с ОС;
- установка копированием папки, две сборки по разрядности (x86 и x64);
- TLS 1.0 через системный SChannel, COM-interop с Outlook и WPF работают штатно.

.NET 8 не подходит: поддержка заканчивается 10.11.2026. Современная альтернатива — .NET 10 (LTS до ноября
2028), но официальной EWS-библиотеки под него нет, только неофициальные порты.

Проекты — в SDK-формате, собираются установленным .NET SDK (референсные сборки .NET Framework 4.8 —
NuGet-пакетом `Microsoft.NETFramework.ReferenceAssemblies`). UI — WPF + MVVM. Хранилище (R2) — SQLite
(`Microsoft.Data.Sqlite`, WAL, версия схемы и миграции) как кэш и журнал. Секреты — Credential Manager
(DPAPI): пароль вводит пользователь, программа и тесты читают его оттуда. Тесты — xUnit + подменные порты.

Данные установки — адрес EWS, ящик, смещение пояса, отпечаток сертификата — в `ConnectionProfile`,
читаются из локального `config/connection.json` (шаблон — `connection.example.json`; реальный файл не
коммитится). В коде, документах и логах конкретных значений нет (T36).

## 16. Реестр ловушек (T1–T36)

### Катастрофические

| # | Ловушка | Следствие | Мера |
|---|---|---|---|
| T1 | Лимит стоял только на создание | Сбой логики → массовое удаление копий | Лимит удаления (20 и ≤10 % копий), стоп и подтверждение |
| T2 | Неполное чтение источника | События «пропали» → удаление корректных копий | `SourceSnapshot.isAuthoritative`; неавторитетный снимок запрещает удаление |
| T3 | Повтор запросов при 401 | Доменная политика блокирует учётку | Аутентификационные ошибки не повторяются |
| T4 | Мусор в «Удалённых» продолжает занимать квоту (перенос ящик не увеличивает) | Первичная заливка поверх → `ErrorQuotaExceeded` | Объём «Удалённых» после очистки и предложение очистить их; проверка квоты перед заливкой; опция `HardDelete` |
| T5 | Два экземпляра приложения | Двойная работа, гонки, дубли | Глобальный мьютекс (+ блокировка в базе в R2) |
| T27 | Режим «все события» при приёмнике = основной календарь | Уничтожение личных событий | В R1 только режим «все» — с предпросмотром, манифестом и подтверждением адресом; в R2 режим «только копии моста» становится режимом по умолчанию |
| T31 | Копии в «чистом UTC» | Все события на весь день растянуты на два дня; повторы с 00:00–04:00 местного — не в тот день | `MeetingTimeZone` с фиксированным смещением из профиля, собственным определением; проверка набором §6.4 |
| T33 | Подтверждение вводом адреса не участвует в запросах | Очистка ушла бы в ящик сохранённой учётки, а не во введённый | Введённый адрес — `Mailbox` в запросах; нет прав на этот ящик → отказ сервера |
